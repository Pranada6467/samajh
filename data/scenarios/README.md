# Datasheet: Samajh scenario set

## What it is

144 synthetic post-sale calls: 36 hand-written base cases, each in Hindi (`hi`), Hinglish (`hi-en`), Tamil (`ta`) and Kannada (`kn`). Each scenario holds a lender's record of a loan sold with one insurance product, what the customer truly believes about that product, and the gold result a correct teach-back call should reach. Each also holds two scripted calls on the same facts: the Samajh teach-back call and a yes/no confirmation call.

Every later measurement (E1 to E5 in `DESIGN.md` section 9) is scored against this set.

Every record, name, id and figure is invented. Loan ids read `TEST-LN-nnn`, call ids `TEST-CALL-...`, and borrower and insurer names end in `(synthetic)`. The set contains no phone number, account number, Aadhaar or PAN, and no text from a real call.

## Files

| File | What it holds | Frozen |
|---|---|---|
| `gold.jsonl` | One scenario per line: record, beliefs, gold, source award | Yes, by sha256 |
| `calls.jsonl` | One line per scenario: both scripted calls, the perfect extraction of the teach-back call, the scripted yes/no replies | Yes, by sha256 |
| `FROZEN.json` | Hash, date and count of both files, with the history of earlier freezes | |
| `CHANGELOG.md` | Every freeze and every change to gold, with the evidence | |

```
uv run python -m samajh.scenarios build     # regenerate both files, byte for byte
uv run python -m samajh.scenarios verify    # exit 1 if a file or the generator differs from FROZEN.json
uv run python -m samajh.scenarios check     # gold against the rule engine on perfect input
uv run python -m samajh.scenarios stats     # the counts below
```

`build` refuses to replace a frozen file whose bytes would change. A deliberate change needs `build --force`, a `CHANGELOG.md` entry, and `freeze --reason "..."`.

Read the files with `samajh.scenarios.load_scenarios()` and `load_calls()`. They return `Scenario` and `CallScripts` objects (`samajh/scenarios/model.py`).

### One row of `gold.jsonl`

- `id`, `base`, `language`, `text_review`.
- `title`, `target_rule`, `scenario_class`, `tags`.
- `record`: a `LoanRecord` as the lender holds it.
- `told`: what the customer was told at the sale, in English.
- `beliefs`: what the customer believes about each product. A field is a value, `"dont_know"`, or `"evasive"` (a non-answer such as "yes, all fine").
- `concerns`: what the customer says about how the sale was handled.
- `customer_state`: `informed`, `misled`, `unaware` or `did_not_agree`.
- `yes_no`, `yes_no_basis`: how the customer behaves on the confirmation call, and why.
- `gold`: the case verdict, and for each product its verdict, the flagged rule ids and the rule ids a human could not decide (`unclear`). `case_flags` holds case-level flags. `rationale` says why.
- `template`: the award the case is modelled on, what was taken from it, what the scenario changes, and the remedy the award ordered. `null` for a synthetic case.

### One row of `calls.jsonl`

- `teach_back.transcript`: a `Transcript` with bot and customer turns. Bot questions carry `asks` and `product_id` as the rule engine needs them.
- `teach_back.extraction`: the `RawExtraction` a perfect extractor would return. Every answer quotes the customer's whole turn. This is the gold for extraction accuracy.
- `yes_no.transcript`, `yes_no.replies` (yes, no or unsure for each of five closed questions), `yes_no.outcome` (`confirmed` only when every reply is yes).

The bot's wording is a stand-in until the script builder exists. The customer's wording is the frozen part.

Classes: `violating` means gold flags the scenario's target rule. `compliant` means gold is clear. `near_miss` means the case looks close to a violation of its target rule and gold does not flag that rule; its verdict is clear or unclear.

## How gold was derived

1. Each base case was written by hand in `samajh/scenarios/cases.py`: the record, the customer's beliefs, and then the gold with a written rationale.
2. Gold applies `DESIGN.md` section 6 as a person reading it would, plus the coordinator's four decisions of 2026-11-10. The table below is the reading used.
3. The rule engine was not run on any scenario before the first freeze. Building the files does not import `samajh.rules`, and a test enforces that.
4. The set was frozen by hash on 2026-11-10, before any audio or extraction was run on it.
5. Only after the freeze was gold compared with the rule engine (see "Agreement with the rule engine"). Each disagreement was decided on the written rules, and each change to gold is in `CHANGELOG.md`.

| Rule | Paragraph (bank / NBFC) | Gold flags it when | Gold leaves it unclear when |
|---|---|---|---|
| `recall` | internal | The customer does not name the product when asked, before any product is mentioned, what they took with the loan (coordinator decision 2) | |
| `kind` | 85Y / 101Y | The customer says it is something other than insurance, or does not know what it is (the second is our reading) | The customer gives no usable answer |
| `premium` | 85Y / 101Y | The stated amount, confirmed at read-back, differs from the record by more than 1% | The customer does not state an amount: "I don't know", "I don't remember", or no usable answer |
| `cover`, `term` | 85Y / 101Y | The customer is wrong or does not know | The customer gives no usable answer |
| `cancel_window` | 85Y / 101Y | The record shows a window and the customer gives another, was told of none, or does not know | The customer gives no usable answer |
| `consent` | 85G / 101G | The record holds no consent; or the customer's own account of what they agreed to buy leaves the product out or is "I don't know"; or the customer describes another way of agreeing than the record shows | The customer agreed but cannot say how (coordinator decision 3), or gives no usable answer |
| `loan_funded` | 85W / 101W | The premium came out of the loan and the record holds no consent, or the customer says it was paid separately, or does not know how it was paid | The record says paid separately and the customer does not know; or no usable answer |
| `bundling` | 85V / 101V | The product was required for the loan, per the record or the customer, and it is not a risk mitigant or no choice of provider was offered, per the record or the customer | The customer does not know whether it was required, or gives no usable answer |
| `belief_mismatch` | 4(20A)(ii) / 6(9A)(ii) | The customer claims a feature the product does not have (a deposit, refundable at any time, withdrawable after a period, a guaranteed return, a single payment), or does not know whether the money can be got back | The customer gives no usable answer |
| `sale_conduct` | internal | The customer says they were told how to answer, learned of the product after the sale, or signed without explanation. This is a case-level flag | |

A product verdict is `flag_for_review` with any flag, `unclear_needs_human` with no flag and at least one unclear rule, and `clear` otherwise. A flag is evidence for a human reviewer. It is never a finding of mis-selling.

Readings that are ours, where the design is silent:

- **"I don't know" about the premium is unclear; about anything else it is a flag.** Section 6 says a premium "not stated" is unclear, and gold reads "I don't know the amount" as not stated. The rule engine flags it instead (see "Agreement with the rule engine"). For cover, term, cancellation, consent and the money-back probe, section 6 itself makes "unaware" or "I don't know" a flag. Section 6 is silent on a customer who does not know what the product is; gold flags `kind` there by analogy (U10).
- **A product recalled under the wrong name is still recalled.** A customer who answers the open question with "just an FD, 52,000" has named the product on record, under the wrong kind. Gold flags `kind`, not `recall`.
- **An evasive reply to the open question names nothing.** In C03 the customer answers "everything is fine". Gold flags `recall` on the letter of section 6. The scripts have no re-ask.
- **A single-payment claim counts under `belief_mismatch`** when the record does not list one-time payment among the product's features (B03). Section 6 gives refundable, guaranteed return and FD as its examples.
- **A customer who agreed to the purchase under a wrong description recognises the consent.** In U08, V04, V06 and C02 the customer says they signed or gave an OTP "for the FD", "for the deposit" or "for the plan". Gold does not flag `consent` there. The misdescription is carried by `kind` and `belief_mismatch`. A reviewer could reasonably hold that such a consent was not informed.
- **`loan_funded` follows the letter of section 6.** In G02 the record holds a signed consent, the customer denies agreeing, and the customer knows the premium came from the loan. Gold flags `consent` and not `loan_funded`.
- **A savings policy is recorded with `kind: credit_life`.** The record type has one product kind in v1. V04 marks the savings policy with `risk_mitigant: false`.

## The yes/no call and what E1 can claim

The confirmation call asks five closed questions built from the record: did you take this insurance policy, is the premium this amount, was it paid this way, did you consent, were the terms explained. It is our model of a confirmation script. It is not a transcript of any lender's or insurer's call.

Each customer has a disposition:

- `truthful` (32 base cases): answers each question by what they believe. Says no when the question contradicts their belief, and "not sure" when they do not know. A stated premium within 5% of what they recall counts as a match. "The terms were explained" gets a no only from a customer who learned of the product after the sale.
- `coached` (3 base cases): was told to say yes to everything. Four awards record such an account (`references/claims/findings-B.md`, B4, B-N5, B-N6, B-N17).
- `acquiescent` (1 base case, U02): says yes to a bank caller without weighing the question. This is our assumption, taken from the demo line in `DESIGN.md` section 10. The source award discusses no call.

What this means for E1:

- **The headline E1 gap is set by the mix we chose.** It is a property of this set, not an estimate of anything in the field. Report E1 by stratum, never as one number alone.
- The yes/no call is not a strawman. A truthful customer who believes the product is an FD, a deposit or an investment says no to "you took an insurance policy". A truthful customer who never agreed says no to the consent question. The scripted yes/no call catches 10 of the 19 base cases where the customer is not informed.
- It misses 9 by construction, and every one of the 9 is our choice:
  - 4 by disposition: the coached customers (C01, C02, C03) and the acquiescent customer (U02). If U02 were truthful, the yes/no call would catch the hero case at its first question.
  - 5 by script coverage: beliefs the five questions never ask about (U06 cover, U07 cancellation window, B01 withdrawal after a year, B02 guaranteed return, B03 single payment). These measure what the closed script covers, not open against closed. A closed script that stated the cover, the window and the premium frequency would catch U06, U07 and B03 with a truthful customer.
- **Disposition is applied to the yes/no call only.** U02, C01 and C02 say yes to everything on the yes/no call and answer the teach-back call candidly, including its yes-or-no-shaped questions (choice of provider, cancellation). Only C03 stays on the yes script in both calls. This assumption favours the teach-back call.
- In B01's award the insurer submitted a recorded call to show the customer had confirmed the policy. The belief about withdrawal is the complainant's account.
- **U05 and R01** are informed customers whom the rules flag (a premium rounded 1.21% off; a product not named unprompted). They carry the tag `flag-on-informed-customer`. Agreement with gold counts them as correct flags. Report them as the rules' cost on informed customers.

## Source awards

11 of the 36 base cases are modelled on public awards. `template.taken` states the fact pattern used, `template.changed` what the scenario invents, and `template.remedy` what the award ordered. Relief in the source awards varied: refund, conversion to a single-premium policy, partial refund, and a premium difference.

- Compliant and near-miss cases are synthetic, written from the rules. No award the insurer won is used.
- An award is a pattern, not a script. Loan sizes, covers, terms, consent records and every spoken line are ours. Several source awards are not about a loan, or concern a loan type the record cannot express (housing, cash credit, overdraft); `template.changed` says so in each case.
- The Baramulla order (G01) was read in a scan hosted by a news site and was passed ex parte.

## Agreement with the rule engine

Run after the freeze with `uv run python -m samajh.scenarios check`. Two paths, both without an LLM:

- `beliefs`: the customer's true beliefs given to `samajh.rules.evaluate` as perfect `Beliefs`.
- `extraction`: the perfect extraction of the scripted text through `samajh.rules.to_beliefs` (amount parser and quote grounding) and then `evaluate`.

Result on version 2 (144 scenarios, 36 base cases; counted from the command's output on 2026-11-10):

| Path | Verdict and flag set agree | Verdicts agree | Flag sets agree | Unclear-rule sets agree |
|---|---|---|---|---|
| `beliefs` | 136 of 144 | 140 of 144 | 136 of 144 | 136 of 144 |
| `extraction` | 135 of 144 | 139 of 144 | 136 of 144 | 135 of 144 |

By base case: 34 of 36 agree on the `beliefs` path. The design expected 100%. The number is 94.4%, and what limits it is one rule reading, not noise:

- **U09 and U10, all four languages (8 scenarios): the premium rule.** The customer says they do not know or do not remember the amount. Gold says unclear, from section 6 ("not stated → `unclear`"). The engine raises a medium `premium` flag. In U09 this changes the verdict (`unclear_needs_human` against `flag_for_review`); in U10 the verdict is `flag_for_review` either way. Gold was kept and the difference reported to the coordinator.
- **U01-ta (1 scenario, `extraction` path only): the amount parser.** The customer says "பன்னிரண்டரை ஆயிரம் ரூபாய், ஒரே தடவைதான் கட்டணும்" (twelve and a half thousand, to be paid only once). The parser reads "ஒரே" as the number 1, finds two amounts and refuses the turn, so the premium is a gap and the product is not clear. The other 143 scripted calls parse to the believed amounts, terms and windows.

On version 1 the `beliefs` path also gave 136 of 144. Three engine-only flags on U10 (`kind`, `consent`, `belief_mismatch`) were gold errors against the current section 6 and were corrected; see `CHANGELOG.md`.

This check measures whether gold and the engine read the rules the same way on perfect input. It says nothing about speech recognition or extraction.

## Using the set

- **Statistics.** The four languages share gold, so the set has 36 independent cases, not 144. Only 9 base cases are gold-clear, so a false-flag rate rests on 9 clusters. Cluster intervals by base case.
- **Extraction scoring.** Compare status and value, not quotes: the expected extraction always quotes the whole turn, and the contract also allows a single whole clause. A customer who says nobody mentioned cancelling has `cancel_allowed: stated false` and `cancel_window: not_asked` in the expected extraction; treat an `unclear` there as equivalent. In U08, V04, V06 and C02 the expected `consent_given` is true (see the readings above); an extractor that returns false on "I signed for the FD" has made a defensible call, and the two should be scored separately.
- **Audio.** Key each customer clip by a hash of its utterance text, not by the hash of `calls.jsonl`. The file hash changes whenever a bot prompt or a read-back wording changes.
- **Git.** The freeze is a hash in a file next to the data. Until the three directories are committed, nothing outside them anchors it. `tests/scenarios` pins the version 1 hash so that history cannot be silently restarted.

## Known limits

- **Templated speech.** Each customer line comes from a phrase bank of one to three variants per answer (`samajh/scenarios/phrases/`). The same sentence recurs across scenarios, and a customer never hesitates mid-sentence, corrects themselves or drifts off the question. Real calls will be messier. Results on this set are an upper bound for the text path.
- **One author.** The same team wrote the rules, the records, the beliefs, the utterances and the gold. An independent model reviewer audited all 36 gold cases and 38 scripted calls (see `CHANGELOG.md`, version 2). No human has reviewed any of it.
- **No fluent Tamil or Kannada reviewer.** Tamil and Kannada rows are labelled `not human-reviewed` in both files. Hindi and Hinglish rows are labelled `model-written, model-reviewed, no human reviewer`.
- **Number words.** Tamil and Kannada amounts use standard written number words with fraction forms. Colloquial forms (அஞ்சு, ரெண்டு) are not used.
- **No re-ask.** The design asks an unclear answer once more in simpler words. The scripts do not model that turn: an evasive customer stays evasive.
- **One product per record, one product family.** Per-product verdicts are stored per product, but no scenario has two products.
- **Not covered:** a customer who names something the record does not hold (`recall_unmatched`); a premium corrected at read-back; a customer who can cancel but does not know by when; a wrong person answering; a customer who declines the call.
- **Coupling.** Gold does not depend on any other package. `calls.jsonl` takes the bot's read-back wording from `samajh.amounts.spoken_amount`, so a change there changes its hash and `verify` will say so.
- **Balance.** The set is built to exercise each rule, not to mirror how often each problem occurs. No rate measured on it says anything about prevalence.
